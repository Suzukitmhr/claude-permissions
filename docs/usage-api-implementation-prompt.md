## 指示文

あなたは、このリポジトリにClaude Code利用イベントの受信APIを実装する担当です。添付または `docs/upstream/usage-api-requirements.md` の「利用イベント受信API 機能要件書」仕様版1.0を実装してください。単なる設計提案で終えず、アプリ・IaC・テスト・運用手順まで作成してください。

### 最初に行うこと

1. このリポジトリのAGENTS.md等と既存構成を確認し、言語・IaC・テスト・CIの標準に従ってください。
2. 要件書の全体を読み、取得元URL・コミットSHA・仕様版を実装先に記録してください。要件書を読めない、または版が一致しない場合は、推測でAPI契約を作らず不足する資料を示してください。
3. 要件書の必須事項と、既存標準に合わせて変更可能な実装技術を区別してください。新規リポジトリならTypeScript、Lambda Node.js 24、AWS SDK v3、AWS CDK v2を採用してください。
4. ローカル実装・テスト・IaCのsynthまで進められるよう、実アカウント情報を含まない設定例を用意してください。AWS環境への変更は実装作業と分け、指定された対象・認証・デプロイ指示に従ってください。

### 実装する内容

- Regional API Gateway REST APIの `POST /events`、IAM認証、許可SSOロールと送信元CIDRの明示的な制限。
- Lambdaでの本文7項目の厳密な検証、利用者・PJ認可、条件付き書込みによる冪等なDynamoDB保存。
- 認証済み `requestContext.identity.userArn` と `caller` に基づく利用者登録。自己申告IDや共通ロール名だけで個人を決めないこと。
- 利用者登録とイベントの2テーブル、保持期限、最小権限、機密情報を含まないログ・メトリクス・アラーム。
- 環境別設定、利用者・PJ権限の登録/無効化手順、SSO権限セット向けInvokeポリシー、疎通・停止・ロールバック手順。
- APIスキーマ、テスト、README。既存の送信フックを変更せず、そのまま接続できること。

詳細なフィールド、正規表現、HTTP応答、保存キー、重複時の挙動、初期制限値は要件書を参照してください。集計画面・CSV・読み取りAPI・Cognito・Bearerトークン・CloudFront・Lambda Function URLは追加しないでください。

### 認証で守ること

IAM認証が検証するのはAWS認証情報です。受信した情報だけから「Identity CenterのユーザーIDが取れた」「人間本人を証明できた」と判断しないでください。SSOの共通ロール名も個人識別子ではありません。

許可したSSOロールの認証済みセッションを、管理者が登録した安定したメンバーIDへ対応付けてください。同じロールの2人を区別でき、同じ人の再ログインでも同じメンバーへ対応付くことを、実環境で受入検証してください。成立しない場合は不合格として報告し、自己申告メールや本文のmember_idへフォールバックしないでください。

認証contextを偽造したLambda直接呼出しが一般利用者からできないようにし、API Gateway経由以外の公開経路を作らないでください。フックやAWS認証のトークンをAPI本文やログへ保存しないでください。

### テストと完了報告

1. 要件書のAT-01〜AT-15に対応するテスト・検証方法を用意し、実行結果を対応表にしてください。
2. 正常系だけでなく、権限拒否、未知の項目、型・長さ・日付・サイズ境界、並列重複、内容競合、永続化失敗、機密情報のログ漏れ、IaCの制約を検証してください。
3. ローカルでは認証済みcontextとDynamoDBをテストダブルに置き換えて構いません。ただし、モックテストだけでIAM・IP制限・SSO個人識別・実Claudeの結合検証が済んだと報告しないでください。
4. デプロイ・実機検証ができない場合も、可能な実装・自動テスト・synthを完了し、必要な環境値と残りの検証手順を具体的に残してください。
5. 最終報告には、変更概要、実行した検証、未検証事項、IaC出力の取得方法、送信側に設定するURL/region/profileの記入方法を含めてください。実値・個人情報は公開PRやソースに貼らないでください。

要件の変更が必要になった場合は、理由・送信側への影響・代案を示し、正本を管理する `claude-permissions` へ変更を戻してください。受信側だけで契約を拡張して完了扱いにしないでください。
